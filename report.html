1. Executive Summary & System Architecture

The Bank Transfer System is a production-grade enterprise web application developed using Spring Boot 3, Java 21, Spring Data JPA, Hibernate, and MySQL (InnoDB). The core engineering objective of this assignment is enforcing stringent ACID transactional guarantees across high-value multi-step financial operations, isolating non-repudiation failure audit trails from rolled-back business contexts, and eliminating concurrency race conditions via atomic database-level update operations.

2. Mandatory Assignment Technical Responses

Question (a)

What would have happened to the money in test 4 without @Transactional?

Demonstration via Task 10 Experiment (Propagation.SUPPORTS):

In Test 4, a transfer of LKR 1,000.00 from Kamal (100001, balance: LKR 45,000.00) to Saman (100003, balance: LKR 10,000.00) was executed with the "Simulate a system failure" checkbox enabled.

Under Production @Transactional(rollbackFor = Exception.class): When the simulated RuntimeException("Simulated system failure after the withdrawal") is thrown immediately following the sender withdrawal, Spring's AOP proxy catches the exception, engages JpaTransactionManager, and issues an explicit ROLLBACK statement to MySQL InnoDB. The preliminary withdrawal of LKR 1,000.00 is completely undone from the database redo/undo logs. Kamal's balance remains strictly at LKR 45,000.00 and Saman remains at LKR 10,000.00.

Under Task 10 (@Transactional(propagation = Propagation.SUPPORTS)): Because the invocation originates from an unannotated controller method, Propagation.SUPPORTS runs without an active transactional context. Therefore, each statement runs under database auto-commit mode:

  1. The atomic debit query customerRepository.debit("100001", 1000.00) executes and is immediately committed permanently to disk. Kamal's balance drops from LKR 45,000.00 to LKR 44,000.00.
  2. The simulated runtime exception is triggered immediately afterward.
  3. Since no encompassing transaction exists, there is no transactional boundary to roll back. The subsequent credit to Saman (100003) is never reached.

Direct Result: The LKR 1,000.00 vanishes permanently from the bank system. The cumulative sum of all customer balances decreases from LKR 85,000.00 to LKR 84,000.00, demonstrating a catastrophic breakdown of Atomicity (the "all-or-nothing" guarantee) and violating the financial invariant of Consistency.

Question (b)

Why is recordFailure in a separate class with REQUIRES_NEW?

This design addresses two fundamental architectural realities of Spring Framework:

1. Preventing Audit Trail Rollback Contamination: When BankService.transfer() fails (due to insufficient funds or simulated system failure), the outer transaction is marked as Rollback-Only and all changes are discarded. If the failure audit record were written within the same transaction, the INSERT INTO bank_transactions would be rolled back as well, leaving zero audit evidence of the attempted transaction. Propagation.REQUIRES_NEW suspends the outer transaction, initiates a separate physical database connection, executes the audit insertion, and immediately commits it independently.

2. Overcoming Spring AOP Self-Invocation Proxy Limitations: Spring manages declarative transactions by wrapping Spring Beans in dynamic runtime proxies (CGLIB / JDK Dynamic Proxies). The proxy intercepts external calls to start and commit/rollback transactions. If recordFailure() were located in the same class (BankService) and invoked via this.recordFailure(), the call would be a direct internal JVM call, completely bypassing the Spring AOP Proxy. Consequently, the @Transactional(propagation = Propagation.REQUIRES_NEW) annotation would be completely ignored. Isolating the method into TransactionAuditService ensures that calls from the controller pass through the Spring proxy, guaranteeing independent transactional execution.

Question (c)

Why does debit use UPDATE ... WHERE balance >= :amount instead of reading the balance first?

Reading the balance first followed by an application-level update creates a critical Time-of-Check to Time-of-Use (TOCTOU) race condition: 

Thread A (Withdraw 40,000): Reads Balance = 50,000.00  | Check Passed (50,000 >= 40,000)
Thread B (Withdraw 40,000): Reads Balance = 50,000.00  | Check Passed (50,000 >= 40,000)
Thread A: Writes Balance = (50,000 - 40,000) = 10,000.00 (Committed)
Thread B: Writes Balance = (50,000 - 40,000) = 10,000.00 (Committed - Overwrites A!)
Result: Customer withdrew LKR 80,000.00, but account was only debited LKR 40,000.00!

By implementing the conditional update: 

@Query("UPDATE Customer c SET c.balance = c.balance - :amount WHERE c.accountNumber = :accountNumber AND c.balance >= :amount")
  • Row-Level Exclusive Locking (X-Lock): In MySQL InnoDB, executing this UPDATE statement against the unique account_number column immediately acquires a row-level exclusive lock. Concurrent transactions are blocked until the current transaction commits or rolls back.
  • Atomic Kernel Execution: The condition check (balance >= :amount) and calculation (balance = balance - :amount) execute in an indivisible CPU instruction inside the database engine.
  • Reliable Row Count Return: The statement returns the number of rows updated (int). If the balance is insufficient, zero rows are modified, enabling the service to immediately throw InsufficientBalanceException with mathematical certainty.
  • Cache Eviction: @Modifying(clearAutomatically = true) automatically synchronizes and clears Hibernate's first-level cache, preventing stale entity reads.
